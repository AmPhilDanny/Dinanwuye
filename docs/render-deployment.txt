# Dinanwuye Render Deployment Runbook
# Updated: 2026-08-26

This project is a monorepo. Node services share the `backend` pnpm workspace,
but Render runs each web service in an isolated runtime. Never put secrets in
Git or frontend `VITE_*` variables.

## Deployment model

Deploy from `AmPhilDanny/Dinanwuye`, branch `master`:

| Service | Render type | Root directory | Build command | Start command | Health check |
|---|---|---|---|---|---|
| Main web app | Static site | `frontend` | `pnpm install --frozen-lockfile && pnpm run build` | Publish `dist` | N/A |
| Admin web app | Static site | `admin-frontend` | `pnpm install --frozen-lockfile && pnpm run build` | Publish `dist` | N/A |
| Auth API | Web service | `backend` | `pnpm install --frozen-lockfile --prod=false && pnpm --filter @dinanwuye/auth-service exec prisma generate --schema prisma/schema.prisma && pnpm --filter @dinanwuye/auth-service... run build` | `node auth-service/dist/main.js` | `/api/v1/health` |
| Profile API | Web service | `backend` | `pnpm install --frozen-lockfile --prod=false && pnpm --filter @dinanwuye/profile-service exec prisma generate --schema prisma/schema.prisma && pnpm --filter @dinanwuye/profile-service... run build` | `node profile-service/dist/main.js` | `/api/v1/health` |
| Messaging API | Web service | `backend` | `pnpm install --frozen-lockfile --prod=false && pnpm --filter @dinanwuye/messaging-service exec prisma generate --schema prisma/schema.prisma && pnpm --filter @dinanwuye/messaging-service... run build` | `node messaging-service/dist/main.js` | `/api/v1/health` |
| Admin API | Web service | `backend` | `pnpm install --frozen-lockfile --prod=false && pnpm --filter @dinanwuye/admin-service exec prisma generate --schema prisma/schema.prisma && pnpm --filter @dinanwuye/admin-service run build` | `node admin-service/dist/main.js` | `/api/v1/admin/docs` |
| Matching API | Web service | `backend/matching-service` | `pip install -r requirements.txt` | `python -m uvicorn main:app --host 0.0.0.0 --port $PORT` | `/health` |

Notification, payment, trust-safety, and api-gateway packages exist in the
repository but are not in `render.yaml`; deploy them only after their routes
and environment requirements are verified.

## Install services in Render

The preferred route is Render Dashboard -> New -> Blueprint. Select the GitHub
repository and the root `render.yaml`, review the service list, then apply it.
If a service already exists, update it instead of creating a duplicate.

For manual creation, use New -> Web Service for APIs and New -> Static Site
for frontends. Set the root directory, build command, start command, publish
directory, and health check exactly as shown in the table. Choose the Free
plan for testing. Deploy APIs before frontends. After changing a `VITE_*`
variable, redeploy the static site because Vite embeds it at build time.

For static sites, set Publish Directory to `dist`. Add a rewrite from `/*` to
`/index.html` when client-side routes return 404 after a browser refresh.

## Where values come from

**PostgreSQL:** Render Dashboard -> New -> PostgreSQL -> Connect -> Internal
Database URL for Render services. Use the External URL only from your local
computer. For Supabase, use Project Settings -> Database -> Connection string.
URL-encode special characters in passwords.

**Supabase:** Project Settings -> API provides the Project URL and publishable
or anon key. The service-role key is server-only. Never put it in a `VITE_*`
variable.

**Secrets:** Generate locally in PowerShell and paste directly into Render:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
node -e "console.log(require('crypto').randomBytes(16).toString('hex'))"
```

Use different values for JWT, refresh-token, and OTP secrets. Use the same JWT
signing secret wherever a service verifies tokens. Rotate any value previously
committed or exposed.

**Redis:** Render Dashboard -> New -> Key Value -> Connect provides the
connection URL. Use the internal URL for services in the same region.

**Cloudflare R2:** Cloudflare Dashboard -> R2 -> Overview provides the
endpoint. R2 API Tokens provides access and secret keys. The bucket name is the
bucket you create; configure a custom public domain only when intended.

## Database initialization

Run this once against the intended production database, using the external URL
from your local machine:

```powershell
Set-Location .\backend
pnpm install --frozen-lockfile
$env:DATABASE_URL = '<external database URL for local administration>'
pnpm --filter @dinanwuye/admin-service exec prisma generate --schema prisma/schema.prisma
pnpm --filter @dinanwuye/admin-service run db:push
pnpm --filter @dinanwuye/admin-service run db:seed
```

Prefer a reviewed Prisma migration for an existing production database.
Confirm the admin seed credentials are changed before real production use.

## Verification

1. Check Render logs for a successful build and the expected start command.
2. Open each health endpoint listed in the table.
3. Test main-app sign-up and sign-in.
4. Test admin login and confirm the browser response includes the matching CORS
	origin header.
5. Test photo upload only after object-storage credentials are configured.

```powershell
render whoami
render services --output json
render logs --resources <service-id> --output json
render deploys create --service <service-id>
```

This Render CLI version has no simple `render env set` command. Set secrets in
the Dashboard or an approved Render API/IaC workflow.

## Local installation and storage

Install Node.js once on Windows. The backend already declares pnpm and its
workspace. pnpm uses one shared store, although each project retains links and
its own build output. To reinstall cleanly:

```powershell
Remove-Item .\backend\node_modules, .\frontend\node_modules, .\admin-frontend\node_modules -Recurse -Force
Set-Location .\backend; pnpm install --frozen-lockfile
Set-Location ..\frontend; pnpm install --frozen-lockfile
Set-Location ..\admin-frontend; pnpm install --frozen-lockfile
pnpm store prune
npm cache clean --force
```

Do not run the removal while a dev server is active. Render services remain
isolated and cannot share one installed Node runtime or `node_modules` folder.

## 🔑 SECRET GENERATION COMMANDS

```bash
# JWT Secrets (run once, use same across all services)
openssl rand -hex 32
# Output example: a1b2c3d4e5f6... (64 chars)

# OTP Secret
openssl rand -hex 16

# VAPID Keys (for web push)
npx web-push generate-vapid-keys

# Database passwords
openssl rand -base64 24
```


## ⚠️ CRITICAL NOTES

1. **JWT_SECRET must be IDENTICAL** across auth-service, profile-service, messaging-service, admin-service, matching-service
2. **DATABASE_URL** — use Render Postgres **internal** URL for service-to-service, **external** for local dev
3. **CORS_ORIGIN** — comma-separated, no trailing spaces
4. **Auto-deploy** is ON for all services (trigger: commit to master)
5. **Health checks** configured: /api/v1/health (Node), /health (Python)
6. **Free tier** — services spin down after 15min inactivity, cold start ~30s
